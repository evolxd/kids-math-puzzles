# PK对战模式 · 产品设计文档

2026-07-31 · 源于一次关于"孩子觉得七年级+的题是work"的grilling会话

## 背景

七年级+那批题（含几道世界级难题）孩子不觉得有趣，原话是"这些都是work"。排查下来根子不是页面不好看（虽然grade7-plus确实还是最老的静态UI），而是**独自闷头解一道道互不相关的抽象谜题这件事本身没有意义感**。孩子提到喜欢Prodigy那种RPG对战游戏，明确表示想要PK（对战），不只是单人闯关。

## 产品策略：不跟Prodigy拼规模，拼它做不到的地方

Prodigy的战斗题本质是包了RPG皮的基础算术题海——为了维持"打怪"的题量，只能走算法批量生成，做不出深度推理题。这正是这个系统一直在做的东西（称重推理、逻辑推演）。所以PK模式不是"缩小版Prodigy"，而是"Prodigy做不到的那个版本"：

1. **胜负只认答对/答得快，不叠装备和随机数**——Prodigy被吐槽最多的就是"答对了还可能输"，战斗结果被装备等级和RNG稀释。做透明的"对即赢"更省事（不用设计装备平衡经济），还更公平、更真实反映孩子的实力。
2. **PK题要快但不能水**——不退化成纯口算（那是Prodigy的地盘），做"压缩版"的找规律/快速逻辑判断，几十秒能想明白，但依然要有"啊哈"感。
3. **异步优先，不做真·实时对战**——真人实时同步（在线状态、断线重连）是Prodigy那个量级团队才该碰的复杂度，先用最小工程量验证"PK"这件事本身有没有用。
4. **继续免费、无账号、无内购**——本来就是既定方向，顺带是对Prodigy会员付费墙的天然口碑优势。

## v1 范围

| 决定 | 选择 | 不做的 | 原因 |
|---|---|---|---|
| 对手 | 邀请码/房间制，只能和主动邀请的人对战 | 陌生人自动匹配 | 产品面向"其他家庭"，跨家庭儿童实时互动涉及审核/隐私合规（COPPA/PIPEDA），责任量级远超一个人能长期维护的免费项目。**列入以后再评估清单，不是永久拒绝**，但需要单独一轮安全设计讨论才能启动，不能顺手加。 |
| 同步方式 | 异步——各自答完存结果，系统比对，出结果通知 | 真·实时对战（双方同时在线、看对方进度条） | 实时同步的工程量（presence、断线重连、双方倒计时）比异步CRUD高一个数量级，先用便宜的版本验证机制本身。 |
| 题库 | 新写一批PK专用快题（30秒-2分钟能想明白），与现有深度谜题库分开 | 直接复用现有143道深度题 | 深度题5-15分钟才能解完，实时/近实时对战会变成一个人苦想、另一个人干等。 |
| 计分 | 正确率+用时直接决定胜负 | 装备/等级/随机数加成 | 更公平、更省设计成本，是这次唯一"又便宜又更好"的选择。 |
| 试点年级 | 七年级+（问题的起点） | 全年级铺开 | 沿用这次一路的节奏：先小范围验证，再决定要不要推广。 |

## 核心玩法（v1）

1. 孩子A在"PK擂台"入口创建一个房间，系统生成一个短房间码（比如6位字母数字），可选一个显示昵称（不是真实姓名，不需要注册）。
2. A把房间码/链接发给认识的人（同学、朋友、兄弟姐妹）。
3. 双方（或多人）各自在自己的设备上，用同一套题目（比如5道PK快题）独立作答，系统记录每题对错和用时。
4. 全部完成后，房间状态变为"已结束"，双方都能看到对比结果（谁对得多、谁更快、逐题比对）。
5. 房间有效期设置为48小时左右，过期自动清空数据——不长期保留任何人的对战记录或身份信息。

## 内容需求

新开一个PK快题库，v1建议先写 **15-20题**（跟grade3-4当初的6题试点、World 7的3题试点一个量级，不追求一次到位）。设计原则：

- 时限感：目标30秒-2分钟内能想清楚，不是"看完题需要读3遍"那种。
- 保留"啊哈"感：优先从找规律、快速排除法、单步逻辑判断这几类里选，不做纯算术口算。
- 题目难度对齐七年级+的水平（这批题原本就是为这个年龄段设计的），不因为"快"就自动降难度。

## 数据模型（Supabase）

刻意做成**不需要账号体系**的最小设计，房间是唯一的持久化单位：

```
pk_rooms
  id            text primary key   -- 房间码，如 "K7X9QP"
  question_set  jsonb              -- 本局用的题目id列表
  created_at    timestamptz
  expires_at    timestamptz        -- created_at + 48h，用于自动清理
  status        text               -- waiting / active / done

pk_participants
  id            uuid primary key
  room_id       text references pk_rooms(id)
  nickname      text               -- 孩子自选，非真实身份
  answers       jsonb              -- [{questionId, correct, seconds}]
  joined_at     timestamptz
```

不建`users`表，不做登录——昵称只在房间内有效，房间过期即清空。这是刻意的隐私设计，不是偷懒：产品服务的是别人家的孩子，能不留存身份数据就不留存。

其余整站（首页、年级页、家长中心）继续保持纯静态+localStorage，Supabase只服务PK这一个孤立功能，不改动现有架构。
